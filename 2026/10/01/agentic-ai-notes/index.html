Agentic AI 学习笔记：从工作流设计到评估优化

发表于2026-10-01|更新于2026-10-01|笔记总结
|浏览量:

Agentic AI 的核心是让基于大语言模型的应用通过多个步骤完成任务：先拆解目标，再调用工具、检查结果，并根据反馈调整后续行动。实际开发中，工作流是否可靠，取决于步骤设计和评估方法，也取决于模型本身的能力。

本文按“基础概念 → 任务分解 → 反思 → 工具与 MCP → 评估优化 → 规划 → 多智能体协作”的顺序梳理知识，并以研究报告、发票处理、客服回复和图表生成为例说明如何落地。

一、理解 Agentic AI

1.1 从单次生成到多步工作流

单次生成把整个任务交给一次模型调用。例如，输入“写一篇关于某个主题的研究报告”，直接取得完整文章。这种方式实现简单、响应快，但缺少检索、检查和修订环节。

多步工作流可以把同一个任务拆成：

  1. 生成研究大纲。
  2. 判断哪些问题需要查资料，生成搜索词。
  3. 搜索并读取相关来源。
  4. 根据证据撰写初稿。
  5. 检查事实、结构和引用，必要时补充检索。
  6. 修订并输出报告。

一个模型可以完成多个步骤，也可以由不同模型分别负责；使用多个模型并不是 Agentic AI 的必要条件。

术语辨析： 零样本提示（Zero-shot）指提示中没有提供输入输出示例；单样本和少样本提示则提供一个或多个示例。它们描述的是提示方式。单次生成与多步工作流描述的是执行结构，因此，多步工作流中的某次模型调用也可以使用零样本提示。

1.2 自主性是一个连续程度

“Agentic”可以用来描述系统具有多少自主决策能力，不必先争论它是否符合某个唯一的“智能体”定义。

自主程度 谁决定步骤 示例 开发重点
较低 开发者预先编排流程 固定执行“提取信息 → 查询订单 → 起草回复” 稳定输入输出和步骤衔接
中等 模型在固定框架内选择分支或工具 判断是否需要搜索，决定是否再修订一次 工具选择、条件判断与停止规则
较高 模型动态规划、执行并调整步骤 根据复杂客服请求自行组合查询与处理流程 计划校验、状态管理与权限边界

自主性提高会扩大可处理任务的范围，也会增加调试难度。流程清晰的任务可以从固定工作流开始，在实际需要时再增加自主决策。

1.3 价值与适用场景

多步工作流的价值主要体现在三个方面：通过检查和修订改善输出；并行处理相互独立的检索或分析任务；把系统拆成可替换、可复用的组件。收益需要通过具体任务的评估确认，更多步骤也会带来额外延迟和成本。

场景 典型步骤 主要难点
发票处理 PDF 转文本 → 提取字段 → 校验 → 保存 日期混淆、文本解析、字段缺失
客服回复 提取问题 → 查询订单 → 起草 → 审核 → 发送 查询正确性、事实依据和语气
研究报告 规划主题 → 检索 → 筛选 → 写作 → 核查 来源质量、重要观点覆盖和引用
数据可视化 读取数据 → 生成代码 → 执行 → 检查图表 数据处理正确性和视觉表达
浏览器操作 观察页面 → 决定动作 → 执行 → 检查状态 页面变化、等待、失败恢复

通常，步骤明确、有标准操作流程、以文本为主的任务更容易实现。步骤未知、需要边执行边决策或处理复杂多模态交互的任务更难。

1.4 四种设计模式分别解决什么问题

任务分解给出工作流的基本结构，设计模式则决定如何组织其中的生成、行动和反馈。

模式 要解决的问题 主要机制 判断是否需要的信号
反思 初次输出存在可以发现和修正的问题 生成后按标准检查，再根据反馈修改 初稿已有基本价值，但经常遗漏约束或细节
工具使用 模型缺少实时信息、精确计算或执行能力 请求工具，执行后把结果送回模型 任务依赖数据库、搜索、代码或业务系统
规划 不同输入需要不同的行动步骤 根据目标和当前状态组织工具调用 固定流程难以覆盖多种请求或条件分支
多智能体协作 单个角色需要兼顾过多职责 按角色分工，并规定结果交接和协调方式 子任务相对独立，需要专业分工或并行处理

四种模式可以组合。例如，一个研究智能体先规划研究方向，调用搜索工具获得资料，由多个研究角色分别分析，再让审查角色检查引用和遗漏。组合后的系统是否更好，要通过相同任务上的评估确认。

1.5 如何判断工作流是否真的带来收益

模型升级与工作流改进是两个不同的变量。比较时可以保留四组结果：模型 A 直接生成、模型 A 使用工作流、模型 B 直接生成、模型 B 使用工作流。这样可以分别观察模型变化和流程变化带来的影响。

比较需要固定任务集、成功标准和可用资料，同时记录工具调用次数、延迟与成本。否则，一个版本使用了更多信息或更多尝试机会，另一个版本只允许回答一次，结果就难以解释。

工作流的收益往往来自三个具体机制：检索补足模型不知道的事实，工具完成模型不擅长的精确操作，反馈帮助发现和修复错误。理解收益来自哪里，才能决定下一步应该增加工具、调整提示，还是更换模型。

二、把任务拆成可执行的工作流

2.1 从人类的做法出发

任务分解可以从四个问题开始：

  1. 人类专家完成任务时，会先做什么、再做什么？
  2. 每一步需要什么输入，应该产出什么结果？
  3. 这一步适合由模型生成、工具执行，还是人工判断？
  4. 如果结果不可靠，能否继续拆成更小的步骤？

模型主要负责理解、生成、提取和决策；工具负责检索、计算、访问业务系统和执行操作。其他模型可以承担 OCR、图像理解、语音等任务。设计时应把“决定做什么”和“真正执行操作”分别落实到相应组件。

2.2 一个完整例子：回复发错货的客户邮件

用户说：“我订购了蓝色搅拌机，订单号 8847，但收到的是红色烤面包机。”

步骤 输入 处理方式 输出
提取信息 客户邮件 模型提取订单号、订购商品、收到的商品和诉求 结构化问题记录
查询记录 订单号 工具查询订单和发货记录 可核实的订单事实
起草回复 问题记录、订单事实、处理规则 模型生成解决方案和回复 邮件草稿
检查与审核 草稿及依据 检查事实、语气和处理权限 通过或修改意见
发送 已通过审核的草稿 邮件工具执行发送 发送状态

如果草稿经常出错，先查看错误来自哪一步。查错订单和回复语气不当，需要修改的组件不同。

2.3 为每一步定义接口

步骤之间尽量传递明确的结构化结果。例如，发票提取结果可以约定为：

明确字段名称、数据类型、日期格式，以及缺失信息的处理方式。没有找到到期日时应返回约定的缺失值，例如 null，并进入补充检查流程；不应把开票日期当作到期日。

原型阶段先跑通少量步骤。只有在某一步表现不佳或难以实现时，再增加分解、反思或人工审核，避免流程无目的地膨胀。

2.4 逐步细化研究报告工作流

同一个写作任务可以从简单流程逐渐细化：

版本 步骤 新增能力 仍需观察的问题
一步 根据主题生成全文 快速得到可阅读结果 缺少外部证据，可能遗漏重要问题
三步 大纲 → 搜索 → 写作 让内容围绕结构和资料展开 来源是否可靠，资料是否覆盖大纲
五步 大纲 → 搜索 → 初稿 → 检查 → 修订 单独处理结构、事实和表达问题 检查意见是否准确，修订是否引入新错误

如果搜索效果差，可以继续拆成“生成查询 → 获取候选来源 → 读取正文 → 按标准筛选”。如果写作遗漏资料中的观点，可以拆成“提取证据清单 → 将证据映射到大纲 → 按章节写作”。分解的目标是让某一步变得可执行、可观察和可评价。

步骤也有合并的理由。如果两个环节长期稳定、没有独立调优需求，拆开只增加调用和数据传递，就可以评估合并是否更合适。

2.5 发票处理的完整链路

发票处理展示了模型和工具如何承担不同职责：

每一层可能出现不同错误。扫描图片模糊属于输入或 OCR 问题；文字顺序错乱可能属于版面解析问题；把“Invoice date”当作“Due date”属于字段理解问题；正确提取后重复写入，则属于保存逻辑问题。

为便于复核，字段可以保留对应的原文片段或页码。系统提取 due_date 后，检查器可以确认它是否来自标有到期含义的区域。金额还应与币种一起保存，避免只有数字而没有业务含义。

在批量任务中，应分别记录解析成功率、字段提取准确率、需人工复核比例和保存成功率。最终只看“保存了多少条记录”，可能掩盖已经保存进去的错误数据。

2.6 用输入输出约定减少错误传播

每一步的约定至少包含：需要哪些字段，哪些字段可以为空，输出如何表示成功或失败，以及下一步在何种条件下可以继续。比如查询订单返回“没有找到”时，写作阶段应请求补充信息，而不是把空结果当作订单事实。

结构校验与语义校验需要分开。due_date 是一个合法日期，只能证明格式可解析；它是否确为付款到期日，还需要结合原文判断。JSON 中存在金额字段，也不能证明提取到了正确金额。

这种约定还方便单独评估组件：固定上一步的正确输出，观察下一步能否完成任务，避免每次调整都必须重新运行全部流程。

三、反思模式：生成之后检查并修订

3.1 反思的基本结构

反思（Reflection）把生成与检查拆开：先得到初稿，再让同一个模型或另一个模型根据标准审查，最后依据反馈修订。

例如，邮件初稿可能存在日期模糊、拼写错误和缺少署名的问题。检查阶段把这些问题具体指出，修订阶段再逐项处理。反思可以是预先编排的固定步骤，不要求系统高度自主。

3.2 写清楚检查动作和标准

“请让它更好”缺少方向。更有效的反思提示需要说明检查什么、如何报告问题、修改时保留什么。

同样的方法可以用于 HTML 标签完整性、代码错误、操作步骤顺序、域名可读性等任务。检查标准应围绕具体失败方式设计。

3.3 使用外部反馈

自我检查仍可能重复模型原有的错误。外部反馈提供新的信息，让修订有可核实的依据。

任务 外部反馈 反馈给模型的内容
代码生成 执行结果、报错、测试结果 代码、实际输出、错误位置与预期结果
数据查询 数据库返回值、查询错误 查询语句、执行结果与业务要求
事实核查 可靠来源的检索结果 待核查说法及支持或反驳它的证据
文案约束 词数统计、规则匹配 当前词数、限制、检测到的违规内容
图表生成 实际生成的图片 绘图代码、图片、数据和评价标准

带外部反馈的循环是“生成 → 执行或检查 → 获取反馈 → 修订”。应设置轮次或时间上限，并以验证结果决定是否继续。

3.4 多模态反思：检查实际生成的图表

以对比两个年份第一季度咖啡销量为例，模型先生成 Python 绘图代码并执行，再把代码和实际图表交给多模态模型检查。

检查重点包括：图表类型是否符合比较目标，标题和坐标轴是否清楚，分组与图例是否易读，数值和单位是否与数据一致。只看代码无法发现所有视觉问题，因此检查对象应包含最终图片。

反思增加了调用次数，是否保留需要比较同一批任务在加入反思前后的质量、延迟和成本，评估方法见第六节。

3.5 检查与修订为什么可以分成两次调用

一种实现让模型一次完成“反思并重写”，调用少、实现简单。另一种实现先输出检查意见，再由修订步骤处理这些意见，便于保存问题清单、核对证据和追踪变化。

检查阶段要回答“哪里不符合要求，依据是什么，如何修改”；修订阶段要回答“如何在保留正确部分的同时修复这些问题”。职责分开以后，可以发现检查器误报，也可以检查修订器是否忽略了有效意见。

例如，代码执行失败时，检查器指出是变量名错误，修订器只需修改对应变量。如果要求模型整体重写，可能顺便改动已经正确的计算逻辑。限定修改范围有助于降低这种额外变化。

3.6 一个具体的邮件反思例子

假设发件人已经给出了会议日期和议题，初稿却写成：

下个月有空的话，我们聊一下项目吧。

检查器可以指出三项问题：没有使用已知日期，没有说明讨论目标，也没有给出收件人可以明确回复的安排。依据已有信息，修订稿可以写成：

我想在 10 月 5 日至 7 日之间与你讨论项目的下一阶段计划，重点确认交付范围和时间安排。你在哪一天方便？谢谢，张三。

这个例子的关键是使用已经提供的事实。若输入没有日期或议题，反思阶段应指出信息不足，或把它们作为待确认项；不能为了让邮件更具体就自行编造。

3.7 反思循环的停止条件

可采用以下停止条件中的一种或组合：全部必需检查通过，没有新的可执行修改意见，达到最大轮次，或者触及时间与调用预算。

还应防止修改效果倒退。例如，第二版解决了长度问题，却删掉了客户真正关心的处理方案。评估应同时检查必要内容与格式约束，并保存每一版结果，必要时选择已经验证过的较好版本。

同一个模型担任作者和审查者，实现最简单，但两者可能具有相似的盲点。换一个模型也不自动解决问题。对于格式、计数、计算或执行结果，优先利用相应工具提供反馈；对于难以自动判断的质量问题，再结合明确的 Rubric 和人工抽查。

四、工具使用：模型请求，程序执行

4.1 工具调用的闭环

工具可以是函数、API、数据库接口或代码执行环境。模型生成工具调用请求，应用程序负责校验、执行，再把结果送回模型。

例如，回答“现在上海几点？”需要读取实时时钟。模型请求时间工具，程序取得实际时间，模型再将结果组织成自然语言。查询订单、检索资料和安排日程也遵循这个闭环。

早期实现可以让模型输出 FUNCTION: get_current_time(...) 等约定文本，再由程序解析。支持结构化工具调用的接口通常会直接返回工具名称和参数，省去自定义文本协议。

无论采用哪种形式，执行器都需要确认工具在已注册列表中、参数符合定义、操作权限允许，并处理异常与超时。执行结果还要关联到对应的调用请求，避免多次调用时混淆。

工具名称和说明会影响模型选择。提供清晰的业务工具，例如“按订单号查询订单”，通常比暴露难以约束的底层操作更容易管理。

4.4 代码执行也是一种工具

固定函数适合稳定的业务动作；代码执行适合灵活的计算和数据处理。面对新的统计问题，可以让模型组合现有编程库完成过滤、分组和计算，不必为每种计算新增专用工具。

执行过程仍然是“模型生成代码 → 隔离环境运行 → 返回输出或错误 → 模型修订”。生成代码应在受限制的环境中运行，并限制文件访问、网络访问、资源用量和执行时间。Python 的 exec() 本身不提供隔离能力。

4.6 工具接口设计和失败处理

一个工具的说明要回答：它做什么，何时使用，参数代表什么，返回什么，可能怎样失败。例如，“查询库存”应说明需要商品 ID，结果表示可售数量还是仓库总数量；“查询时间”应说明时区格式。

问题 典型表现 处理方式
工具选择错误 用描述检索回答实际库存 明确各工具职责，给出必要的使用示例
参数错误 商品 ID 缺失，日期或枚举非法 返回具体校验错误，让模型修正参数
找不到数据 订单号合法，但记录不存在 明确返回空结果，进入补充信息分支
执行失败 网络超时或服务暂时不可用 按错误类型决定重试、替代或停止
结果被误读 将查询失败解释成“没有库存” 区分成功、空结果和失败状态
重复执行 重试导致重复创建订单 对有副作用的操作使用去重标识和业务状态校验

查询失败、查询成功但结果为空，是两种不同状态。错误返回应使模型能够分辨原因，避免把基础设施问题转写成错误的业务结论。

4.7 固定工具与代码执行如何选择

固定工具可以把业务规则封装在程序中。例如，退货工具内部验证订单、时间范围和状态，模型只需提供合适的参数。它适合边界明确、要求稳定的操作。

代码执行允许模型自由组合过滤、计算和绘图逻辑，适合需求变化较大的数据分析。代价是需要验证代码、输入假设和运行环境，执行边界也更宽。

两者可以配合：业务系统通过受约束工具返回数据，代码环境负责对这些数据做统计，最终操作仍交由定义明确的业务工具处理。这样既能保留计算灵活性，也能把业务状态变化落实到可检查的接口。

五、MCP：标准化连接工具和数据

5.1 MCP 解决什么问题

MCP（Model Context Protocol，模型上下文协议）由 Anthropic 于 2024 年发布，提供连接 AI 应用、外部工具与数据源的标准接口。Anthropic 发布说明

假设有 mmm 个应用和 nnn 类外部系统，分别开发适配可能形成接近 m×nm \times nm×n 组集成。标准接口允许应用侧连接能力和服务侧封装复用，可用 m+nm+nm+n 描述这一思路；这只是架构上的简化，不代表实际开发成本严格按该公式变化。

5.2 三个参与方与三类服务能力

参与方 职责
Host AI 应用，管理模型交互和一个或多个 MCP Client
Client Host 内连接特定 MCP Server 的组件
Server 提供外部能力的程序，可以运行在本地或远端

Server 可以提供三类不同能力：Tools 是可调用的操作，Resources 是供应用读取的上下文数据，Prompts 是可复用的提示模板。三者应分别理解。MCP 架构文档

例如，总结仓库 README 时，应用通过 MCP 取得文件内容，再交给模型生成摘要。MCP 统一连接方式，工具质量、参数校验和操作权限仍需由应用与服务端落实。

5.3 一次 MCP 工具使用的逻辑过程

从应用的角度，可以把过程理解为：Host 建立 Client 与 Server 的连接，了解服务提供的能力，把需要的工具说明交给模型；模型请求某个操作后，Client 将请求传给 Server，Server 执行并返回结果，再由 Host 把结果送回模型。

例如，用户要求总结仓库 README，模型需要的是文件内容。服务端可以提供读取仓库文件的工具，应用获得内容后再调用模型写摘要。如果用户随后要求查看近期 Pull Request，就需要另一项查询能力。模型决定请求哪项能力，具体访问由服务端完成。

5.4 标准协议与业务实现各自负责什么

MCP 主要统一能力发现和交互方式，减少重复集成。业务实现仍需要处理数据格式、访问权限、错误返回和服务质量。连接成功，不等于每次查询都能得到准确、完整的资料。

也不必把 MCP 理解成所有应用共用一个中央服务器。不同能力可以来自不同服务，本地和远端服务也可以并存。应用应只连接任务需要的能力，并清楚展示每项操作的来源。

六、建立评估，让改进可以验证

6.1 从一个小型测试集开始

评估（Evals）的作用是回答：系统现在表现如何，修改后是否更好？早期可以先建立能跑通的原型，手动检查约 10–20 个代表性任务，再针对重要失败方式建立评估。这个规模适合发现问题和快速迭代，不能据此断言系统在所有场景都可靠。

评估样例应包含输入、任务约束，以及可获得的参考答案或评分标准。比如发票任务保存正确到期日；研究报告任务保存应覆盖的关键观点；文案任务保存统一的长度上限。

6.3 用 Rubric 约束 LLM 裁判

对于文章清晰度、图表表达等任务，单纯询问“这份结果好不好”很难得到稳定评价。评分量表（Rubric）应把评价拆成可观察的标准。

例如，给图表设置四项检查，每项通过记 1 分：

  1. 标题准确说明比较对象和时间范围。
  2. 坐标轴有标签，单位明确。
  3. 图表类型支持当前比较目标。
  4. 分组、图例和数值范围能够清楚呈现数据。

要求裁判返回每项得分及依据，再汇总总分。这个量表评价的是表达质量；数据计算是否正确，需要单独核对。

比较两个版本时，应在同一批任务上使用一致的评分标准。若采用成对比较，可交换展示顺序以检查位置偏差，并用人工抽查确认裁判是否符合实际质量判断。

6.4 同时保留端到端和组件级评估

评估层级 回答的问题 例子
端到端 用户最终得到的结果是否合格？ 研究报告是否准确、完整、引用可核实
组件级 某一步是否完成了职责？ 搜索是否找到关键来源，提取日期是否正确

端到端评估决定产品能否满足目标。组件级评估则适合快速定位和调整，减少其他步骤随机性带来的干扰。常用顺序是：通过端到端结果发现问题，沿执行过程定位组件，在组件级调优，最后再做端到端回归。

6.5 评估反思的实际收益

把“直接生成”和“加入反思”的版本在同一测试集上运行，比较正确率或 Rubric 得分，同时记录耗时与调用成本。若准确率从 70% 升到 78%，提升是 8 个百分点，不能含糊写成“提升 8%”。

是否保留反思步骤，要看收益是否满足应用需求。可以只在执行失败、违反规则或检查未通过时触发修订，并设定最大轮次。反思后的结果还需要验证，不能把“已经修改”当作“已经正确”。

6.7 怎样选择和维护测试样例

初始样例应覆盖真实使用中的主要情况，而不是只挑容易成功的任务。发票场景可以同时包含不同版式、扫描件、多个日期、缺少到期日等输入；客服场景可以包含正常订单、订单不存在、信息冲突及需要人工决定的情况。

为便于对比，保留一批固定样例，并记录使用的模型、提示、工具配置和评分规则。针对某个错误反复调优的样例属于开发集，还应留出未参与调优的样例，检查改进是否能够推广。

失败案例值得补进回归集，但它们不应完全替代代表性样例。只有困难样例的测试集适合检查某类错误是否修复，却不能直接估计整体用户请求的成功率。

小测试集的分数变化需要谨慎解释。例如，10 个样例中少错 1 个就会提高 10 个百分点。对于波动明显的工作流，可以在相同条件下重复运行并查看结果分布，再决定是否扩大评估规模。

6.8 不同指标测量的是不同目标

指标 适合判断 常见误用
完全匹配准确率 日期、分类标签等有明确答案的输出 不做格式标准化，把同一答案的不同写法判为错误
约束通过率 长度、必填字段、格式是否满足规则 只看格式，忽略内容是否正确
观点覆盖率 是否讨论了指定重要观点 将关键词出现当作完整论述
精确率与召回率 检索或筛选中相关结果的质量与覆盖 参考集合不完整，却把所有未列出的来源判为无关
Rubric 得分 按统一标准观察清晰度、结构等质量 标准含糊或一次修改了任务、裁判和评分尺度

业务目标可以包含必须通过的检查和可逐步优化的质量分数。例如，订单号错误应直接判为任务不合格，而语句是否足够简洁可以用评分衡量。一个高平均分不能抵消关键事实错误。

6.9 评估系统本身也需要检查

如果人工认为结果改善了，评估却完全没有变化，应检查指标是否遗漏了重要目标；如果得分提升但输出仍然明显不合格，应检查模型是否迎合了评分规则，以及裁判是否误判。

对一部分样例进行人工复核，比较人工和自动评价的分歧，并查看分歧原因。更新评分规则后，应重新运行需要比较的版本，避免把旧尺度与新尺度的分数直接放在一起。

评估代码也有边界。例如，字符串匹配可以检查禁止出现的名称，但会受到大小写、别名和词语歧义影响；如果业务只禁止在特定语境中提及某公司，单纯字符串命中就不能代表违反规则。

七、错误分析：找到最值得改进的步骤

7.1 查看 Trace 和中间结果

一次任务的 Trace 记录各步骤的执行过程，可以包括输入、模型输出、工具调用、返回结果、错误、耗时和成本。单个操作或阶段可记录为一个 Span。

研究报告遗漏关键观点时，沿过程检查：搜索词是否覆盖问题，搜索是否找到可靠来源，筛选是否保留关键信息，写作是否使用了已有证据。只看最终文章，容易把检索问题误判为写作问题。

发票到期日出错也应先区分两种情况：如果 PDF 转出的文本已经丢失日期，应改进解析；如果文本中日期清楚，但模型选了开票日期，应改进字段提取。

7.2 对失败案例分类并统计

建立一张错误表，记录样例、失败现象、出错步骤和证据。优先检查最终结果不合格的案例，再统计每类问题出现的频率。

错误类别 在所分析失败案例中的占比，示例 可能的改进方向
搜索词不合适 5% 补充领域词、明确查询目标
搜索结果质量差 45% 调整搜索服务、时间范围和结果数量
来源筛选错误 25% 明确来源优先级和筛选标准
最终写作遗漏信息 30% 加入关键观点清单和覆盖检查

这些比例仅用于演示，分母是所分析的失败案例，并非全部请求。一个案例可能包含多个问题，因此比例之和可以超过 100%。还需区分上游错误引起的后续失败与独立错误，避免重复归因。

频率是安排优先级的依据之一，还应考虑影响程度、修复成本及改进能否传递到最终结果。

7.4 一个发票错误的逐步定位例子

假设原发票同时包含两行：Invoice date: 2026-10-02 和 Due date: 2026-10-20，最终记录却把到期日保存为 2026-10-02。

从这个过程可以判断：解析器已提供足够信息；格式校验没有能力区分日期语义；保存工具也没有改动字段。首先应改进提取步骤，例如强调两个日期的区别，提供混淆样例，并要求保留字段依据。

如果解析文本只剩下一个没有标签的日期，结论就不同了。此时应检查版面提取或 OCR，或者让系统识别信息不足并进入复核流程。相同的最终错误，可能有不同根因。

7.5 用正确的上游结果隔离问题

一种实用方法是把某一步的真实输出替换为人工确认的正确输入，再观察下游表现。例如，给写作组件提供高质量参考资料，检查它是否仍遗漏关键观点。

如果使用正确资料后报告明显改善，说明检索或筛选是重要因素；如果仍然遗漏，则需要继续检查写作提示、资料组织或篇幅分配。这种替换能帮助定位问题，但只是诊断手段，最终还要在真实工作流中验证。

还应避免把受上游错误影响的组件一律判为独立失败。订单查询返回了错误客户的信息，后续邮件引用错误事实，首先需要修复查询；同时可以评估下游是否应增加用户与订单的一致性检查。

7.6 优先级不只看错误次数

优先级可以综合四个因素：问题出现频率、对用户结果的影响、预计改进空间、实施和维护成本。这是一种工程判断方法，并不要求所有因素都有精确数值。

例如，错误事实的频率低于措辞不够自然，但前者影响可能更大。又如，搜索服务质量差涉及很多失败案例，但更换服务后仍可能被筛选器丢弃，因此改进要同时验证信息能否到达最终输出。

一次尽量调整一个主要变量，再用同一套评估比较。这样即使改进没有成功，也能知道哪个假设没有得到支持。

八、按证据优化质量、延迟和成本

8.1 根据出错组件选择方法

组件类型 优先尝试的改进
LLM 理解或生成 明确指令、加入输入输出示例、提供必要上下文
单步任务过于复杂 继续拆分，或加入有针对性的检查与修订
模型能力不匹配 用固定评估集比较不同模型
网页搜索、RAG 调整查询、分块、结果数量、阈值，或替换服务
PDF 解析、代码执行 检查工具实现、输入质量、运行环境和错误处理

模型选择应围绕实际任务评估，不能只根据模型名、参数规模或个人印象。不同步骤可以使用不同模型，但每次替换都应确认质量、速度和成本的变化。

对于需求稳定、数据积累充分的成熟任务，可以进一步评估微调是否值得投入。原型阶段通常先解决提示、上下文、工具和步骤设计问题。

8.2 先计时，再优化延迟

记录每一步的耗时，分析完整路径中的瓶颈。有依赖关系的步骤需要等待上游；相互独立的搜索、网页读取或子任务可以并行。

除了并行，还可以尝试更快的模型、减少无效调用、控制不必要的长输出。每次提速后都要重新检查任务质量。

8.4 提示、上下文和模型分别怎样改进

改进提示时，先补上目标、约束和输出格式，再增加确实能够解释错误的示例。比如提取到期日时，示例应包含开票日期与到期日同时出现的情况，而不只是重复展示普通发票。

改进上下文时，检查模型是否拿到了完成任务所需的信息。材料缺失时，再详细的写作提示也不能提供事实；材料很多但组织混乱时，可以先提取证据，再按章节分配。

更换模型时，以任务中的实际职责为单位比较。字段提取可以重点看准确率和结构稳定性，审查可以看发现真实问题的能力，写作可以看事实使用和表达质量。不要把某个单独任务的表现推广成模型在所有任务上都更好。

如果提示需要同时要求“搜索、筛选、解释、验证、排版”，且错误经常难以定位，可能需要重新分解步骤。继续增加说明，有时只会让单次调用更复杂。

8.5 优化上下文与重复工作

记录每个步骤真正需要的输入，只传递完成当前职责所需的信息。例如，写作阶段需要证据和来源，通常不需要保留搜索接口每次失败的完整调试日志；错误分析系统则应另行保存这些记录。

对于可以重复使用的解析结果和稳定资料，可以考虑缓存，减少反复读取与处理。对于库存、价格等变化较快的数据，应明确缓存有效期或重新查询条件，避免提速后失去时效性。

成本优化还包括减少无效重试。参数校验失败应先修正参数；服务持续不可用时应切换策略或停止，不能无限重复相同请求。工具结果足以完成任务后，也应避免没有目的地继续检索。

8.6 从原型到成熟系统的分析方式

阶段 主要问题 重点活动
快速原型 工作流能否完成任务？ 手动看输出和 Trace，找明显失败
初步评估 改动是否真的改善质量？ 固定小型测试集，建立端到端指标
系统分析 最值得改进的是哪里？ 对失败分类、归因和统计
组件调优 如何快速比较具体方案？ 固定组件输入，比较提示、模型和工具配置
持续运行 新输入和服务变化是否造成退化？ 维护回归样例，跟踪质量、耗时和成本

这些阶段会反复交错。新功能可能需要重新做原型，新错误可能需要更新评估，模型或工具改变后也可能需要重新定位问题。构建和分析都应成为开发流程中的正常工作。

九、规划模式：动态决定行动顺序

9.1 让模型生成计划，再逐步执行

固定工作流由开发者决定步骤；规划（Planning）让模型根据任务和可用工具决定步骤，并在取得新结果后调整计划。

例如，用户问“有没有售价低于 100 元且有库存的圆形太阳镜？”系统可以先查商品描述，再查候选商品的价格和库存，最后筛选结果。仅查询商品的请求不需要创建订单。

自然语言计划适合阅读，但下游程序需要明确的结构。以下是一个自定义计划格式：depends_on 表示依赖，input_from 表示执行器要从上一步结果中取得字段；它不是某个工具 API 的现成参数格式。

执行器需要校验结构、检查工具和依赖、解析实际结果引用，再生成符合工具 Schema 的参数。取得候选商品后，价格与库存查询可以独立执行，最后按实际结果筛选。

计划结构合法，只说明程序能读取它；步骤是否合理、权限是否允许、结果是否满足目标，还需要分别检查。运行中还应保存任务状态，设置调用预算、停止条件和失败后的处理方式。

对于聚合、过滤和排序，代码可以更直接地表达多个步骤。例如，分析“哪一个年月的热巧克力销量最高”，可用 Pandas 完成：

9.3 预先规划与边执行边规划

预先规划先列出主要步骤，再按顺序执行。它适合任务目标清楚、依赖关系相对稳定的情况，计划本身也方便人工或程序审查。

边执行边规划则在每次获得结果后决定下一步。例如，搜索第一次返回的来源不足，模型再生成新的查询；找到一个关键研究方向后，再围绕它补充资料。这种方式能够应对未知信息，但需要记录当前进度，避免反复处理相同问题。

两者可以结合：先制定高层计划，例如“定位产品 → 核实价格和库存 → 整理答复”，每个阶段内部再根据实际结果决定更细的行动。

9.4 计划执行需要保存哪些状态

计划中应区分“准备做”和“已经完成”。写出“查询库存”只代表计划包含这一动作，只有工具返回并被核实以后，才能把它记为已完成。

对于研究任务，状态可以记录已查阅来源、已回答问题和仍缺少的证据。这样模型在调整计划时能够基于进展决策，而不是重新从任务开头开始。

9.5 将计划校验拆成三层

第一层检查结构：JSON 是否可解析，步骤标识是否唯一，依赖是否存在，是否出现循环依赖。第二层检查可执行性：工具是否可用，参数是否满足定义，上游是否已经提供所需数据。第三层检查业务合理性：行动是否有助于目标，是否在允许范围内，是否满足关键操作的前置条件。

例如，计划安排“处理销售订单”，但用户只问库存，这个步骤即使结构合法、工具也存在，仍不符合当前任务。又如，计划在商品 ID 尚未取得时查询价格，就需要先解决依赖。

如果检查不通过，可以把具体原因送回模型修改计划；错误信息应指出哪一步、哪项约束出了问题，避免只返回“计划无效”。

9.6 失败恢复与完成标准

恢复方式应取决于失败类型：参数错误需要修正；暂时的服务错误可能适合有限重试；没有符合条件的商品也是有效的查询结果，可以据实答复；权限或业务前提不满足时需要停止相应动作。

完成标准应来自用户目标。例如，商品查询至少需要确认相关候选商品的价格和库存，才能报告它们是否满足条件；研究报告则需要完成规定的主题、来源和检查要求。

达到调用上限时，系统应说明已经确认的结果和剩余缺口。不能因为计划执行结束或模型宣称“完成”，就默认目标已经达成。

十、多智能体协作：围绕职责分工

10.1 什么时候拆成多个智能体

当一个任务包含明显不同的职责，或者单个智能体需要同时处理过多工具和上下文时，可以拆成多个角色。例如，研究员负责搜集证据，分析员负责统计和结论，写作者负责表达，审查者负责核对事实与引用。

多个智能体可以使用同一个底层模型。差异来自各自的任务、提示、工具和上下文。这样做有利于独立调优和复用组件，也可能通过并行减少耗时；同时会增加调用、协调和信息传递开销，需要通过评估判断收益。

10.2 四种常见通信结构

结构 信息流 优势 主要限制
线性 研究员 → 分析员 → 写作者 简单，容易追踪 顺序依赖明显，需额外设计回退
双层 管理者分配任务、汇总子智能体结果 协调集中，职责清晰 管理者可能成为瓶颈
多层 管理者 → 子团队 → 更细分角色 支持大型任务分解 层级多，调试和信息保真更难
去中心 多个智能体按规则相互通信 灵活，适合探索 需控制消息数量和终止条件

两方“执行者—审查者”协作也很常见，适合生成与审核职责明确的任务。初次实现可以从简单结构开始，只有在职责或并行需求确实增加时再扩展。

10.3 设计好交接内容

每个角色都应有明确的输入、输出和完成标准。交接结果除了结论，还应包含关键证据、来源、未解决问题和必要的结构化数据。

只传递摘要可以缩短上下文，但可能丢失决定结论的细节。多智能体并不会消除上下文限制，而是把信息分布到不同角色，并依靠交接保持必要信息。应让管理者能够追溯证据，也避免让所有智能体无差别地读取完整历史。

10.4 将角色落到任务和工具上

一个角色名称只是起点。还需要规定任务范围、可用工具、结果格式和完成标准，才能让职责产生实际差异。

角色 主要输入 工具或能力 必需输出
研究员 子问题、范围和来源标准 搜索、网页读取、文档提取 事实、证据片段、来源与未解决问题
分析员 研究结果或结构化数据 数据处理、代码执行 方法、计算结果、假设与限制
写作者 大纲、已核实结论和证据 内容组织与表达 正文、引用位置和待确认内容
审查者 草稿、约束和原始证据 规则检查与事实核对 问题清单、证据和修改建议
管理者 总体目标和各角色结果 任务分配、状态跟踪与汇总 最终结果、覆盖检查和剩余缺口

例如，给研究员的任务可以写成“查找支持子问题的可靠资料，返回具体证据和来源；资料不足时报告缺口”。这比“你是世界一流的研究专家”更能限定实际工作。

角色之间可以使用同一模型，但工具、任务和上下文应与职责一致。写作者需要组织已核实的信息，不应默默把尚未验证的猜测改写成确定结论。

10.6 并行分工与顺序依赖

可以并行研究不同子问题，但写作需要等待必要证据。审查可以提前检查已完成章节，最终核查则需要看到完整报告及其来源。

并行的前提是子任务能够独立推进，并且不会争用同一份需要修改的状态。如果多个角色同时编辑同一文档或业务记录，需要明确谁拥有修改权，以及如何合并结果。

管理者还应检查不同子任务的口径是否一致。例如，某个研究员讨论实验室环境，另一个讨论露天果园，汇总时不能直接把两者的数据作为同一条件下的比较。

10.7 常见协作失败及处理方式

失败方式 为什么发生 可尝试的处理
重复劳动 子任务边界不清楚 明确每个角色的研究问题与排除范围
信息丢失 多层摘要只保留结论 保留证据引用，让下游可以追溯原文
结论冲突 使用不同资料、定义或时间范围 汇总时核对口径，并显式保留未解决分歧
管理者负担过重 所有细节都经过同一个角色 子任务内部完成基本检查，返回必要结果
消息循环 角色不断要求对方进一步讨论 规定可执行反馈、轮次上限和完成条件
交接后无法使用 输出格式和下游输入不匹配 为接口定义必需字段和验收检查

增加角色数量会带来更多通信和整合工作。只有当分工解决了现有的上下文、专业职责或并行瓶颈时，复杂度才有明确收益。应将多智能体版本与职责相同的简单工作流比较，而不是仅凭角色数量判断能力。

十一、把知识连成一个开发闭环

以研究报告智能体为例，可以按下面的顺序逐步开发：

  1. 明确目标和约束。 约定主题范围、篇幅、来源要求、引用方式及完成标准。
  2. 实现最小流程。 先跑通“大纲 → 搜索 → 阅读 → 写作”，记录中间结果。
  3. 观察代表性样例。 检查是否遗漏观点、选错来源、缺少证据或引用失效。
  4. 建立小型评估。 为部分主题准备关键观点，使用代码检查格式，使用 Rubric 检查覆盖与表达。
  5. 定位主要错误。 区分查询、检索、筛选和写作问题，对频繁或严重的失败优先处理。
  6. 改进组件并回归。 调整工具、提示、模型或步骤，再确认最终报告质量。
  7. 按需要增加反思与规划。 用核查结果触发修订，让模型在信息不足时决定补充检索。
  8. 在职责清晰时引入多智能体。 独立研究方向可以并行处理，由管理者汇总并保持来源可追溯。
  9. 测量并优化耗时与成本。 对关键路径、昂贵步骤和无效重试进行优化，同时保留质量评估。

这套流程会反复循环：构建 → 观察 → 评估 → 错误分析 → 改进 → 回归验证。评估指标和测试集也需要随着真实失败案例更新，才能持续反映用户对系统的要求。

11.1 贯穿开发过程的四类记录

任务记录 保存用户目标、输入和约束，便于重现问题。执行记录 保存工具请求、返回结果、计划变化和中间输出，便于定位原因。评估记录 保存参考答案、评分依据和版本配置，便于比较改动。运行记录 保存耗时、Token、重试与费用，便于优化资源。

这些记录对应不同问题，不应只保留一份最终回复。在研究报告场景中，至少需要能够追溯某个说法来自哪里，以及该来源在筛选和写作阶段如何被使用。

11.2 一个可复用的实践检查清单

设计环节 检查问题
目标 怎样判断用户任务已经完成？有没有必须满足的约束？
分解 每一步的输入、输出和执行者是否明确？
工具 名称、参数、返回值、错误状态和权限是否清楚？
反思 检查依据是什么？修订后由谁验证？何时停止？
评估 测试集是否覆盖真实情况？指标是否对应实际目标？

规划 依赖和状态是否可检查？失败后能否恢复或据实结束？
协作 角色边界和交接证据是否明确？管理者如何处理冲突？
优化 瓶颈是否经过测量？提速或降本后质量是否仍合格？

学习这些模式时，可以先围绕一个熟悉的任务实践。例如，从几张发票开始，完成解析、提取、评估和错误分析，再尝试反思；随后把同样的开发方法迁移到研究报告或客服流程。这样更容易理解每个新增组件解决了什么问题。
